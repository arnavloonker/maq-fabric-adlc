# /verify procedure

1. **Scope.** Resolve the consumer repository root via Git and `maq-project.json`. Identify story ID and target version (commit SHA, artifact IDs/versions). Reject paths escaping the root.
2. **Context.** Read the story (`azure-devops-wit_work_item` `get`, `list_comments`), its approach section, PR/commit diff, and only relevant domain records. Consult /best-practices for each artifact type reviewed; do not claim consultation if retrieval failed, and surface failures.
3. **Contract.** If the story holds an approved contract/seam, copy it to `contract.json` with `origin: reused-from-approach`. Otherwise (or if scope/criteria changed) draft one: criteria, target version, DEV environment, permitted checks, data limits, expected evidence, cleanup. Present it and wait for explicit engineer approval. No approval: verdict `blocked`, stop.
4. **Discover tools.** Inspect available schemas for the needed read/query surfaces (e.g. `FabricIQ-ExecuteQuery` for bounded DAX, SQL endpoint read-only query). Substitute only when semantics, scope, permissions and approval boundaries are equivalent; a generic SQL executor that can mutate is not equivalent to a read-only query. Record substitutions.
5. **Dispatch reviewer.** Launch `maq-adversarial-reviewer` in a separate context with: story, approach, exact diff/artifact versions, domain records, approved contract. It evaluates claims independently of the implementer's summary and returns findings per criterion. If it cannot be launched, verdict `blocked`; do not substitute the current context.
6. **Run checks.** Execute only `permittedChecks` in DEV, within `dataLimits` and timeouts. Per check record: criterion id, expected, actual, tool/query identity, environment, operation ID, start/end UTC. Use aggregates; mask or exclude sensitive rows. Stop at the first out-of-scope need and report it; request renewed approval rather than widening scope.
7. **Staleness.** Immediately before publishing, re-read HEAD/PR source commit and each live artifact's definition version/modified time. If any differs from the contract target, mark all earlier evidence `stale`, set verdict `inconclusive`, and offer to re-verify the new version (new run-id, renewed approval if scope changed).
8. **Verdict.** Apply the contract's rules: `passed`, `failed`, `blocked` or `inconclusive`. Report only what ran; list untested criteria.
9. **Save evidence.** Create (never overwrite) `references\stories\<story-id>\verification\<run-id>\` with `contract.json`, `evidence.md`, `results.json`. Run-id: UTC `yyyyMMddTHHmmssZ` plus 6 hex chars. Mark publication `local/unpublished` until committed via an approved commit or an approved ADO attachment; preview any index or existing-file edit.
10. **Preview comment.** Render the ADO comment: verdict, story/version tested, criteria table (expected vs actual), untested areas, reviewer findings, staleness check time, evidence location (published link or explicit "local/unpublished"). It must be readable without the evidence files. Show it and wait for approval.
11. **Post.** Call `azure-devops-wit_work_item_comment_write` with `add` and the approved text. On timeout, do not retry blindly: `list_comments` first and reconcile by run-id; if inconclusive, stop and report.
12. **Read back** the comment and report its URL, verdict, evidence path and blockers. Never change story state, fix code, approve or merge the PR, or close anything.
