# /verify procedure

1. **Scope.** Resolve the consumer repository root via Git and required platform identifiers from `maq-project.toon`. Identify story ID and target version (commit SHA, artifact IDs/versions). Reject paths escaping the root.
2. **Context.** Read the story (`azure-devops-wit_work_item` `get`, `list_comments`), its approach section, PR/commit diff, and only relevant domain records. Consult /best-practices for each artifact type reviewed; do not claim consultation if retrieval failed, and surface failures.
3. **Contract and target.** Reuse the approved contract/seam with `origin: reused-from-approach`; if absent or changed, propose one. Recommend lower-environment runtimes from `maq-project.toon`: DEV by default or UAT for explicitly prompted, concretely approved validation under governing safety. Resolve a user-prompted target's live identity, environment, permissions and policy before asking for exact engineer approval. Capture artifact versions, workspace ID, permitted executions/checks, quantitative expectations/tolerances, data windows, limits, both proof tiers and cleanup. Changed operations, targets or versions need renewed approval. PROD remains read-only; explain prohibited operations without silently changing targets or claiming read-only observations prove runtime execution. No approval: `blocked`.
4. **Discover runtime skills and tools.** Match each artifact and operation to `capability-matrix.json`, load the installed companion skill, and discover its actual tool schemas and prerequisites. A `planned` row means unvalidated support, not automatic refusal: validate the live route and proceed with approved operations when supported. Record matrix status, limitations and substitutions; do not relabel the matrix without separately approved evidence/publication. Recommend branch isolation or a shared lower-environment prefix. If the prompt explicitly targets an existing workspace/unprefixed artifact, record exact approval, rationale and mode (`branch-workspace`, `shared-prefix`, or `user-directed-target`) and proceed; missing isolation alone does not block validation. If identity, permission or an installed supported binding cannot be established, report that concrete blocker rather than improvise.

   | Artifact / operation | Installed runtime skill |
   | --- | --- |
   | Notebooks, SparkJobDefinitions, Lakehouse loads | `spark-cli` |
   | Warehouse SQL execution | `sqldw-cli` |
   | SQL database execution | `sqldb-cli` |
   | Dataflows Gen2 refresh | `dataflows-cli` |
   | Semantic model refresh/query and DAX | `semantic-model-authoring`; `fabriciq` for natural-language model queries |
   | Real-Time Intelligence ingestion/query | `eventhouse-cli` / `eventstream-cli`, according to artifact |

   Use the skill appropriate to the actual operation, not every skill in a row. A model query does not prove refresh succeeded, nor does an Eventstream start prove downstream ingestion. Substitute only equivalent semantics, scope, permissions and approval boundaries; a mutating SQL executor is not a read-only fallback.
5. **Dispatch reviewer.** Launch `maq-adversarial-reviewer` in a separate context with: story, approach, exact diff/artifact versions, domain records, approved contract. It evaluates claims independently of the implementer's summary and returns findings per criterion. If it cannot be launched, verdict `blocked`; do not substitute the current context.
6. **Execute artifacts, then reconcile.**
   - Re-read each approved artifact definition version/timestamp before execution. Trigger its real runtime operation through the discovered skill/tool; record artifact name, item ID/type, version, tool/skill, environment/workspace, run/job/operation ID and UTC start in `executions[]`. Do not silently deploy or modify a definition to make it run.
   - Poll asynchronous jobs/refreshes to terminal state with a bounded polling deadline. Record UTC end, duration and normalized `Succeeded`/`Completed`/`Failed` plus raw provider status. For synchronous SQL/DAX, capture actual operation identity and completion. Never invent IDs/statuses; a timeout or still-running job is inconclusive, not successful. Reconcile unknown submissions before retrying; no duplicate runs. Failed or cancelled required executions prevent `passed`; record diagnostics and skip dependent checks, while retaining permitted independent checks.
   - Only after the required upstream runs complete successfully, execute `permittedChecks` at the seam and upstream boundaries against the same version, filter window and parameters. Reconcile source-to-target counts with filters/joins and rejects/quarantine; test key uniqueness and declared grain, schema/null boundaries, and applicable SQL/DAX aggregates. Record expected, actual, delta and approved tolerance with units; deviations outside tolerance fail.
   - In `checks[]`, link execution IDs and capture criterion, boundary, sanitized query/command, skill/tool, environment/workspace, version, operation ID and UTC start/end. Separate observed values from implementer claims. Mark inapplicable or skipped checks with reasons, never as executed passes.
   - Honor approved limits: stated query purpose, at most 250 returned rows, and 60-second query timeout/budget where supported. Polling deadlines are separate from query budgets. Bound scans with predicates; disclose unsupported enforcement. Use aggregates, exclude sensitive rows and redact credentials without removing reproducibility. Out-of-scope work or cleanup needs renewed approval.
7. **Staleness.** Immediately before publishing, re-read HEAD/PR source commit and each live artifact's definition version/modified time. If any differs from the contract target, mark all earlier evidence `stale`, set verdict `inconclusive`, and offer to re-verify the new version (new run-id, renewed approval if scope changed).
8. **Verdict.** Apply the contract's rules: `passed`, `failed`, `blocked` or `inconclusive`. Require successful runtime evidence in `executions[]` and reconciled criteria in `checks[]` at the current target version, with independent review, before `passed`. Static review alone never passes. Report only what ran; list missing tiers, failures and untested criteria. Resolve reviewer disagreements explicitly; do not suppress them.
9. **Save evidence.** Create (never overwrite) `references\stories\<story-id>\verification\<run-id>\` with `contract.json`, `evidence.md`, `results.json`. Run-id: UTC `yyyyMMddTHHmmssZ` plus 6 hex chars. Mark publication `local/unpublished` until committed via an approved commit or an approved ADO attachment; preview any index or existing-file edit.
10. **Preview comment.** Render the same seven-section Validation Report from [the evidence template](evidence-template.md), not a compressed verdict-only note: executive verdict and story/version/environment/workspace; runtime execution table; criterion reconciliation table; data quality/grain; separate-context reviewer agreements/disagreements; risks/untested scope; reproducibility commands, sanitized queries, windows and parameters. Include IDs, UTC timing, tolerances, staleness recheck and evidence location (published link or explicit "local/unpublished"). It must be readable without the evidence files. Show the exact sanitized text and wait for separate ADO publication approval.
11. **Post.** Call `azure-devops-wit_work_item_comment_write` with `add` and the approved text. On timeout, do not retry blindly: `list_comments` first and reconcile by run-id; if inconclusive, stop and report.
12. **Read back** the comment and report its URL, verdict, evidence path and blockers. Never change story state, fix code, approve or merge the PR, or close anything.
